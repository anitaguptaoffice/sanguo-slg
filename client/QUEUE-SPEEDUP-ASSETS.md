# Queue speedup asset receipts

CLIENT-QUEUE-SPEEDUP-ASSETS-001, issue #2043. The existing queue action still submits exactly one UseConsumable(2003, 1); no new item or consumption path is added.

Queue speedup now uses the same asset mutation coordinator as the bag. A fresh confirmed receipt may apply its absolute remaining count and full wallet_after, including genuine zero gold. If another read or asset change overtook the receipt, existing bag/city reads reconcile current snapshots rather than restoring an older remaining count. Confirmed consumption survives subsequent city-refresh failure and is never replayed automatically. Queue city reads also check asset epoch and bag/wallet references before overwriting resources; city snapshots still preserve last-known gold.

Unknown consumption or failed reconciliation locks further speedup use in the current queue context and directs the player to Refresh Queue. That explicit action reloads bag/resources and building state before unlocking; failure retains the guard. Reopening the panel alone does not unlock. No read claims whether the old operation succeeded, and a timed-out server command may still settle later. The existing ListPlayerBag endpoint can trigger the existing starter grant; this change does not add new grants or receipt identity. Stale actor/session/lifecycle/operation responses cannot update a replacement operation.

Regression evidence: eight new assertions fail on base, four control cases pass. Mounted queue tests exercise concurrent real shared bag helper use, full receipt zero, old city reads, unknown/reconciliation failures, explicit read-only retry, repeat prevention, lifecycle changes and confirmed-result preservation. One earlier lifecycle test intentionally changes its unsafe expectation of immediately retrying unknown consumption. Full tests/build, independent final-tree review, and exact-head/main CI are recorded in PR evidence. No browser/live acceptance, deployment or hold release is claimed.
