# Recruit durable transport and caller identity

Task [SPEC-RECRUIT-TRANSPORT-001 / #1899](https://github.com/anitaguptaoffice/sanguo-slg/issues/1899), base `dcd1f01c212ac2dd42b5c1aab14c87e2d520a6c4`. This is a SPEC-only proposal, not a proto change, implementation, activation, or restart-test claim. [COMMAND](MIL_RECRUIT_COMMAND.md), [QUEUE](MIL_RECRUIT_QUEUE.md), and [STORAGE](MIL_RECRUIT_STORAGE.md), and [RULE EVIDENCE](MIL_RECRUIT_RULE_EVIDENCE.md) remain authoritative, including their transaction, retained identity, catalog, and provenance gates. This does not alter DATA-002 or gameplay.

## 1. Observed boundary and selected route

At this base [military.proto](../proto/sanguo/military/v1/military.proto) allocates `RecruitTroopRequest` fields 1 `int64 city_id`, 2 `int32 unit_cfg_id`, 3 `int32 count`; no identity/version fields or reservations are present. Its response fields 1 `CityTroopStack troop`, 2 `ResourceWallet wallet`, 3 `int64 queue_id`, 4 `int64 finish_at_ms` describe legacy live-ish state, not immutable acceptance. [envelope.proto](../proto/sanguo/common/v1/envelope.proto) has packet route, session, shard and per-attempt trace; response carries code/data/trace. Trace is correlation only.

The existing [handler](../../internal/api/military_handlers.go) checks current city ownership before `RecruitWithWallet`, returns wallet/troop snapshots and runs quest follow-up. It is not durable receipt readback. `playerCtx` in [server.go](../../internal/api/server.go) resolves the bound session and verifies a supplied nonzero shard matches; a packet shard is not authority. The checked-in [Go generated client](../../internal/api/pb/sanguo/military/v1/military.pb.go), browser [loadProto](../../client/src/net/loadProto.ts) and [GatewayClient](../../client/src/net/GatewayClient.ts) use the existing route/messages. The browser RPC creates a fresh trace UUID per attempt and times out; [decodeGatewayResponse](../../client/src/net/decodeGatewayResponse.ts) converts int64 to numbers only after rejecting values outside JS safe range, so it cannot carry the full accepted cost range; [MainCityScene](../../client/src/scenes/MainCityScene.ts) presently writes response wallet/troops into session and treats a failed submit as an error. None supplies durable command identity. These observations are not guarantees about a deployed version.

Select a separate route `military.v1.RecruitTroopV2`, with new protobuf messages `sanguo.military.v1.RecruitTroopV2Request` and `RecruitTroopV2Response`. This avoids a new request silently reaching an old handler that ignores unknown fields, and prevents old decoders treating historical acceptance as current stock/wallet. Actual proto and generated code require a separate reviewed contract PR; recheck route, field and error allocations at that PR's base. Do not alter or repurpose the legacy fields.

## 2. Exact wire contract

Request fields, proto3, with these names, types and numbers:

| # | field | type | constraint |
|---|---|---|---|
| 1 | city_id | int64 | exact intent |
| 2 | unit_cfg_id | int32 | exact intent |
| 3 | count | int32 | exact intent |
| 4 | command_id | bytes | exactly 16 bytes and not all zero |
| 5 | intent_version | uint32 | exactly 1 for new acceptance |

No actor, shard, price, timestamp, trace, or catalog input is in intent. Compare typed `(intent_version, city_id, unit_cfg_id, count)` exactly, within trusted `(server_id, authenticated player_id, operation=RecruitTroop, command_id)` scope. Operation is the same logical RecruitTroop in both semantic/storage contracts, not a new V2 dedup namespace. Version is outside unique key scope. Existing accepted same-key different tuple/version is conflict; do not reject an unsupported or zero version before the post-barrier historical comparison in a way that hides such conflict. Compare the complete wire uint32 without truncation, wrapping or narrowing in the APP/domain bridge: values 0, 2, 32768, 65537 and 4294967295 cannot alias version 1. Only after certified absence and exact equality to 1 may implementation narrow it to the existing receipt smallint value 1. If no accepted key exists, only version 1 may create an acceptance; missing/zero/malformed ID or version cannot spend. Exact validation of invalid city/unit/count follows the semantic admission contract. No handler-generated key or trace ID substitution.

`RecruitTroopV2Response` success contains exactly one `RecruitAcceptance acceptance = 1` message. The acceptance's field allocations are:

| # | field | protobuf type | meaning |
|---|---|---|---|
| 1 | queue_id | int64 | positive retained queue identity |
| 2 | city_id | int64 | accepted city |
| 3 | unit_cfg_id | int32 | accepted unit |
| 4 | count | int32 | accepted quantity |
| 5–8 | food_paid, wood_paid, iron_paid, stone_paid | int64 each | exact four paid amounts, nonnegative; no gold |
| 9 | duration_sec | int64 | positive integral duration |
| 10 | initial_status | int32 | 0 waiting or 1 active, at acceptance only |
| 11–13 | accepted_at_ms, initial_start_at_ms, initial_finish_at_ms | int64 each | signed Unix milliseconds, canonical finite UTC instants |
| 14 | catalog_version | bytes | exact 75 ASCII bytes of the retained version string (`recruit-v1:` plus 64 lowercase hex digits), no terminator |
| 15 | rule_digest | bytes | 32-byte trusted SHA-256 rule digest |

All fields represent the immutable receipt, including estimates for initially waiting work, not today's queue phase, current price, wallet or troop stock. The response has no raw job JSON and no live state. Status 0 is a valid value despite proto3 defaulting; presence of the acceptance message and validation of its full invariants distinguish success from missing/malformed data. Milliseconds and IDs must round-trip signed 64-bit values exactly; JS clients use protobuf Long/bigint or checked decimal representation, never lossy `number` arithmetic. The encoder and decoder must also range-check int32/int64 and preserve the exact bytes of command ID, manifest identifier and digest; paid amounts may use the full nonnegative int64 range. The existing safe-number decoder is insufficient for this response. Timestamps meet QUEUE's 0001–9999 millisecond range and checked duration/time arithmetic. Acceptance payload is identical in value for first success and historical retry; envelope trace may differ. Client associates reply with the persisted in-flight attempt, not an echoed trace as identity. No command key echo is required in the acceptance port.

## 3. Authentication, outcomes and readback

Every attempt authenticates the current session and validates account ownership of the bound player and trusted shard, including actor existence, as COMMAND requires. Client-provided packet `server_id` may only be checked against that binding, never select another actor/shard. An expired/revoked session is unauthorized; reauthenticate the *same* account/player/shard before retry. Other namespaces reveal nothing about a key in the original scope.

After actor and initialized-wallet barrier, exact-key receipt/origin lookup and queue→receipt locking/re-read/validation follow COMMAND and STORAGE. A validated historical receipt returns the immutable acceptance even if the city now has a different owner or readiness; it must not run current-city ownership validation first, mutate, repair or re-debit. A genuinely new acceptance still requires current city owner/readiness, complete capacity and catalog checks, and atomic debit/job/origin/receipt commit. Trace/logging must not create a second debit or claim replay was new. The existing `questAfterTrainTroops` is nontransactional and not shown idempotent: V2 MUST NOT invoke it on replay or blindly invoke it after an uncertain outcome. Any quest delivery is a separate reviewed idempotent/atomic integration gate, not provided by this specification.

Wire errors use existing `COMMON_INVALID_PACKET` 10001 for malformed encoding/key or unsupported version on eligible absence, `COMMON_UNAUTHORIZED` 10002 for invalid authentication, `COMMON_UNAVAILABLE` 10003 for unavailable source/fence/catalog or inconsistent/orphaned identity, and proposed new `MILITARY_RECRUIT_INTENT_CONFLICT` 50008 for same scoped accepted key with different typed intent. 50008 is unallocated in the base envelope; independently recheck all allocations before proto approval. 10003 deliberately does not reveal whether origin, job or receipt exists and is not proof of rollback. Business rejection codes apply only after authenticated, serialized readback establishes certified absence and the request definitively fails before commit; they must not represent timeout, lost commit acknowledgement, orphan, or unverified absence. Map a definitively invalid count, proposed-count representable-capacity failure, or request-specific cost/duration/schedule arithmetic overflow to `MILITARY_INVALID_TROOP_COUNT` 50002; unknown unit to `MILITARY_INVALID_UNIT` 50001; insufficient wallet to `MILITARY_INSUFFICIENT_RESOURCE` 50004; validly determined unmet recruit prerequisites to `MILITARY_RECRUIT_NOT_ALLOWED` 50003; and current city not owned or absent to `WORLD_CITY_NOT_FOUND` 30001. An already-invalid aggregate, malformed state, untrusted catalog or inability to distinguish invalid state from a business rejection is 10003, not 50002. These mappings introduce no new queue limit. Server must not fabricate acceptance, infer absence from one missing half, or use a current state read to prove rejection. No persisted rejection ledger is promised; mismatch is detectable only against accepted receipts.

A transport timeout, disconnect, malformed/missing reply, server internal failure, commit-ack loss, client crash, or session change is **unknown**, not rejection. Retain the exact key and intent and retry the same route under the same authenticated scope. Fresh authoritative readback waits for wallet serialization and, with a valid epoch, finds acceptance or certified absence after resolution; uncertainty or invalid provenance remains unavailable. On explicit conflict stop and surface a diagnostic; never replace the key to bypass it. A definite business rejection has no accepted receipt, but the key→intent binding remains immutable; a later deliberate new user action may use a newly generated key, never automatic retry under a new key. Current wallet/ready troops and live queue must be separately refreshed through authorized current-state reads and labeled current, not reconstructed from acceptance. Failure to refresh does not undo acceptance.

## 4. Durable caller journal and UI

Before the FIRST network send, caller generates 16 cryptographically random bytes, rejects all-zero, and durably commits one atomic journal record `(stable account identity, bound shard, player identity, operation, command_id, intent_version, city_id, unit_cfg_id, count, state)` with exact integer/byte encodings. The key and tuple cannot be edited; preserve them across retries, tab reload and process restart. Use a collision-safe unique local key and retry generation before send on local collision. No network send if randomness, transaction commit, quota, serialization, storage access or durability verification fails. Do not put credentials/session tokens in the journal. A journal is not a server-side rejection ledger or proof of a server commit.

Browser implementation must use a transactional durable store (e.g. IndexedDB with strict durability where supported), wait for transaction completion and validate readback before send. Support is conditional on a store whose configured durability meets the implementation's reviewed crash/restart requirements; fail closed for the action when storage is unavailable, denied, ephemeral *when known*, corrupt, or cannot establish those requirements. Ordinary localStorage, sessionStorage, memory, best-effort writes and a successful UI animation are not durable proof. The client cannot universally detect private mode, eviction, user deletion, device loss or backup rollback, and browser APIs cannot guarantee against them. Do not claim otherwise. The supported guarantee covers identified commands whose exact committed journal record survives the supported browser/process crash. If a record is missing or lost, never infer rejection or automatically reconstruct/retry the unresolved action under a new key. An affected known unresolved action remains unavailable without its exact identity. Strong cross-device or journal-loss recovery is separately scoped; this contract does not require a global journal-history proof before first use.

On startup/reload, validate schema, full tuple, key length/nonzero, scope, integrity and journal completeness to the extent the store can establish it; quarantine invalid, partial, duplicate-inconsistent, unrecognized-version or *known* restored/uncertain records and stop the affected unresolved actions. Integrity checks detect some corruption, not malicious changes or complete deletion. Never auto-repair, truncate or discard unknown records to resume an affected action. Migrations preserve unresolved entries atomically or block them. Concurrent tabs coordinate a single atomic journal creation/claim and cannot issue two keys for one user action; repeated clicks while unresolved show pending and retry the same record. A deliberate, distinct new user action is not a retry and may use a new key and spend again, including on a clean device; the caller must not relabel a retry as such. No missing local record proves that an earlier command was rejected or never sent.

Account/player/shard switching suspends in-flight UI updates and keeps the original scoped journal; never replay it under another scope or delete it on logout. After authenticating the original scope, resume same-key readback. If a late reply arrives after a switch, correlate to its original record and validate before recording, but do not apply it to the new session. Persist a validated acceptance atomically before displaying resolved; if result persistence fails or reply is lost, remain unknown and replay the same key. Keep unresolved records until resolution; keep resolved key→intent records while retries are supported, since server keys do not expire. UI labels acceptance/initial estimates as historical and separately refreshes current state; never merge accepted cost or estimates into wallet/ready troops as live values.

## 5. Rollout and verification gates

This specification alone enables nothing. Before exposing V2, independently review/freeze the actual proto, generated clients and mappings; notify ACCOUNT, DOM, WORLD, MIL, API/gateway and browser owners. Certify semantic/storage, source-bound one-shot transaction ports, trusted retained catalog, fresh-cohort provenance, allocator, restoration, through-commit epoch interlock and all writer/legacy fences described in the paired contracts. Implement and independently test durable caller journal plus authenticated V2 server together. All incompatible legacy Recruit/stock/queue/Hub/callback writers for the cohort must be drained/fenced, including old clients and alternate endpoints; server must reject legacy write route before any effects in an enabled cohort. A V2 client must never fall back to legacy on unknown route, unavailable, timeout, downgrade or failed capability check. Unknown capability means disabled, not a retry to V1. No mixed-writer enablement or rollback to legacy for a cohort with potentially accepted V2 commands without a separately reviewed safe drain/reconciliation/fence. Existing legacy operation outside a certified cohort is not represented as retry-safe.

Future tests must include exact protobuf bytes/field and int64 round trips; invalid/zero key and version; same key/equal intent under concurrent sends and restart; changed city/unit/count/version conflict, including full uint32 versions 0, 2, 32768, 65537 and MaxUint32 without wraparound or premature narrowing; distinct actor/shard isolation; ownership change after acceptance; no wallet/troop masquerading as live; unknown/commit-ack loss before and after commit; orphan/missing rule/fence/source drift; restored/partial/lost evidence; storage commit/quota/private mode failures; browser restart, multiple tabs, account switch and lost reply; unknown route and rollback attempts with no legacy spend. Verify response persistence failure remains same-key retryable and independent current reads cannot override historical outcome. Real process/crash and database evidence are separate implementation acceptance, not established by this document. Coherent restoration cannot prove history when all identity evidence has been deleted; a complete audit alone is not provenance. These limitations are activation blockers, not permission to infer absence.
